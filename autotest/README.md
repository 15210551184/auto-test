# 页面自动化数据验证工具

给一个页面地址，自动识别页面结构、生成验证用例、执行并产出报告。

## Web 控制台（推荐）

### 按系统管理，勾选要测的菜单

1. **新建系统** —— 填首页地址、登录页地址、账号密码（或留空读 `.env`）
2. **扫描系统菜单** —— 自动展开左侧菜单树，逐个访问，识别每页有没有表格、
   能不能导出、能不能新增。带表格的页面会自动打勾（推荐）
3. **勾选要测的菜单** —— 可以只测订单相关，或全选；选择会自动保存
4. **生成用例** —— 给勾选的页面各建一份配置。已有配置不会被覆盖，
   你手工补的业务断言不会丢
5. **执行测试** —— 跑勾选的页面，全程只登录一次，产出一份合并报告

登录信息放在系统级，改密码只改一处，不用改每个页面的配置。


不用每次 SSH。启动后浏览器打开 `http://服务器IP:5000`：

```bash
docker compose up -d --build     # 或 python server.py
```

界面能做四件事：选配置执行、只测登录、扫描新页面生成配置、看历史报告。
执行过程日志实时推送，能看到跑到第几条用例，不是黑盒等待。
关掉页面任务照常跑，重新打开会接上。

控制台自己有一道登录（`.env` 里配 `WEB_USER`/`WEB_PASS`），没登录会跳转到登录页，不配的话默认放行——部署到公网服务器前务必配置，详见下面的部署文档。

详细部署步骤见 [DEPLOY_DOCKER.md](DEPLOY_DOCKER.md)（通用服务器 Docker 部署）
和 [DEPLOY_1PANEL.md](DEPLOY_1PANEL.md)（1Panel 面板部署，容器编排 + 网站反代）。

## 快速开始（命令行）

```bash
pip install playwright pyyaml pandas openpyxl
playwright install chromium

# 1. 可选：配置账号密码（未配置也可直接启动）
mkdir -p runtime && cp .env.example runtime/.env && vi runtime/.env

# 2. 验证能否登录
python cli.py test-login configs/order_list.yaml

# 2. 扫描页面 + 立即执行（一步到位）
python cli.py auto http://43.114.176.231/web/order/list

# 或者分两步，中间人工调整配置
python cli.py scan http://43.114.176.231/web/order/list -o configs/order.yaml
python cli.py run configs/order.yaml --headed
```

## 设计思路

### 1. 为什么是「扫描生成 + 人工补充」，而不是全自动

全自动听起来最理想，但有个绕不过去的边界：

- **结构性规则机器能判断**：搜索「手机号=222」后，手机号列是不是都含 222；
  时间筛选后创建时间是否落在区间内；导出行数是否等于分页总数。
  这类规则只依赖页面结构，可以自动推导。
- **业务规则机器判断不了**：订单金额是否应该等于实付金额加平台抵扣；
  某个状态下司机字段是否允许为空。这些要读需求文档才知道。

所以分工是：扫描器自动生成 80% 的结构性用例（这部分最枯燥、最费时），
人工补 20% 的业务断言（这部分最有价值）。硬做全自动的结果通常是
生成一堆「断言行数大于 0」的废用例，跑得再快也抓不到 bug。

### 2. 分层架构

```
cli.py                 命令行入口
engine/
  scanner.py           页面扫描 → 生成配置草稿
  runner.py            执行引擎：上下文、编排、快速失败
  actions.py           动作/断言注册表（加能力 = 加函数）
  adapters/
    element_ui.py      UI 框架适配层
  normalize.py         值归一化（页面 vs Excel vs 接口）
  export_verify.py     导出下载与校验
  report.py            HTML/JSON 报告
```

关键分界是 **adapters 层**。`.el-form-item__label` 这类选择器全部关在里面，
上层动作只调 `ui.fill(page, label, value)`。换 Ant Design 只要照同样接口
写一个 `antd.py`，配置和用例一行不用改。

### 3. 配置驱动，不写脚本

用例是 YAML 里的声明，不是 Python 代码：

```yaml
- name: 搜索-下单人手机号
  steps:
    - fill: { label: 下单人手机号, value: "222" }
    - search: null
    - assert_column_all: { column: 下单人手机号, contains: "222" }
```

这样测试同学不用会 Playwright 也能加用例，页面改了改配置就行。
代价是灵活性——遇到特别复杂的交互还是得写代码，所以 `actions.py`
留了注册机制，写个函数加 `@action("xxx")` 就能在配置里用。

### 4. 三个容易被低估的技术点

**值归一化是成败关键。** 页面显示 `73.06 ¥`，Excel 里是 `73.06`，
接口返回 `7306`（分）。不做归一化，任何比对都会 100% 误报。
`normalize.py` 处理金额符号、千分位、多种日期格式、时间戳、空值别名
（`-` / `--` / `无` / `N/A`）。

金额比对的容差刻意设成 0.001 而不是 0.01——1 分钱的差异正是要抓的
舍入 bug，容差放宽就把它漏过去了。

**等接口比等元素稳。** Element 表格没有可靠的 loading 结束信号，
`wait_for_timeout` 是玄学。用 `expect_response` 等列表接口返回，
既准确又顺手拿到了接口原始数据。

**接口数据和表格渲染对比，是投入产出比最高的断言。** 后台系统里
「接口返回对但前端展示错」的频率远高于接口本身出错——金额单位搞混、
时区差 8 小时、状态码没映射全。`assert_api_matches_table` 专抓这类。

### 5. 导出验证

导出是这类页面最容易出问题也最少被测的功能。四层校验：

1. 文件能下载、非空、能解析（xlsx / xls / GBK 编码的 csv）
2. 表头包含页面上所有业务列
3. 行数等于分页总数（导出应是全量，不是当前页）
4. 抽样行字段值与页面一致（归一化后比对）

特别值得测的是「导出是否遵循搜索条件」——筛选后导出却导了全库，
是很常见且很严重的越权/数据泄露问题，配置里单独留了一条用例。

两种导出模式：`direct` 点按钮直接下载，`async` 点按钮只建任务、
需轮询任务接口拿链接（大数据量后台常见）。设 `auto` 会先试前者、
超时自动退到后者。

### 6. 用例隔离与快速失败

每条用例执行前重新 `goto` 页面，不复用上一条的筛选状态——
用例之间互相污染是这类工具最常见的假失败来源。

用例内部一旦失败立即停止后续步骤：后面的步骤依赖前面的状态，
继续跑只会产生一堆无意义的连带失败，淹没真正的错误。

失败自动截图 + 记录控制台报错和 5xx 请求，报告里直接能看到现场。

## 登录

配置里的 `login` 段启用 UI 自动登录：程序打开登录页、填账号密码、点按钮。

**密码放 `runtime/.env`，不要写进 yaml**（yaml 要进 git）。配置里用 `${env:AUTOTEST_PASS}` 引用。
`runtime/` 和 `auth/` 登录态目录已在 `.gitignore` 里。

**懒登录**：每次执行先用已存的 cookie 试目标页，失效了才真正登录。
这样一天可能只登一次，不会在业务系统里堆登录日志或触发异地登录风控。
运行中途 session 过期也会自动重登。

登录框定位默认自动探测（覆盖 name/placeholder/type 等十几种常见写法）。
探测失败会明确提示你在配置里填 `user_selector` / `pass_selector` / `submit_selector`。

**有验证码就用不了**。程序会提前识别图形验证码、滑块、短信验证码并直接报错，
不会让你干等超时。这种情况回退到本地登录：在有图形界面的机器上跑
`python cli.py login <url>`，把生成的 `auth/state.json` 传到服务器同一路径。

密码错误时会把登录页上的真实提示读出来（如"账号或密码错误"），
而不是笼统的登录超时。

### 多个系统，账号不一样怎么办

Web 控制台里每个「系统」都有自己独立的一份 `login`（存在 `projects/<系统名>/project.yaml` 里），互不影响：

- **多个系统共用一套账号**：新建系统时账号/密码留空，都会读 `.env` 里共享的 `AUTOTEST_USER`/`AUTOTEST_PASS`
- **每个系统账号不一样**：在 `.env` 里给每个系统各起一对变量名，比如：
  ```bash
  SYSA_USER=account_a
  SYSA_PASS=password_a
  SYSB_USER=account_b
  SYSB_PASS=password_b
  ```
  新建系统时账号框填 `${env:SYSA_USER}`、密码框填 `${env:SYSA_PASS}`（跟 yaml 里 `${env:AUTOTEST_PASS}` 是同一套引用语法，账号密码框直接支持）

**不要把真实密码直接打进网页的账号/密码框。** `project.yaml` 是会被 git 跟踪的（`.gitignore` 只忽略了 `projects/*/pages/`），如果表单里填的是明文密码，就会原样存进这个文件，跟着仓库走。只填 `${env:变量名}` 引用，真实密码就只留在服务器的 `.env` 里（已在 `.gitignore` 里，不会进 git）。

## 落地路径

1. 配 `.env`，`test-login` 验证能登进去
2. 对第一个页面 `scan`，人工调配置跑通（主要是补接口字段映射）
3. 遍历左侧菜单，对每个列表页跑 `scan` 批量生成骨架
4. 按页面重要性排序，逐个补业务断言
5. 接 CI：`run` 返回非 0 退出码即失败，报告作为构建产物

## 已知边界

- 扫描器只认 Element UI。其他框架需要写对应 adapter。
- 新增/修改用例只能生成骨架（字段名、校验规则机器猜不出来），
  生成时默认 `skip: true`，填完字段再打开。
- 测试数据会污染环境。建议用独立测试账号，或给造出的数据打
  `auto_` 前缀便于清理。
- 强依赖 label 文本。页面文案改了配置要跟着改——这是配置驱动的固有代价，
  换来的是不用写代码。
